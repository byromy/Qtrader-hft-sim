# 架构与运行说明

[返回项目首页](../README.md)

本文说明行情怎样送到策略、订单簿怎样更新，以及如何运行测试和文件回放。
所有命令均在仓库根目录执行。

## 策略如何接收行情

`UftMarketDataEngine` 使用启动期注册的整数合约 ID、固定容量订阅数组和回调指针分发委托、成交事件。
策略直接接收委托和成交事件，不需要先构建完整订单簿。解析器仍会维护订单剩余量，供撤单、改单和成交处理使用。

`UftBookMarketDataEngine` 扩展专用的 `UftBookUpdate` 通道，`UftOrderBookPipeline` 用它更新行情簿，再通知读取盘口的策略。
普通成交回调会过滤不可打印成交，并对成交编号去重；重建订单簿却必须处理每一笔挂单扣量，因此使用单独的更新事件。
当前封装的行情簿入口为单合约、单会话、单线程和一个策略回调。扩展多合约需要上层管理多个实例；
每个实例的序号检查仍须接收整个通道的全部消息，不能先过滤其他合约再把不连续的全通道序号交给它。

## 订单簿怎样处理行情

`UftOrderBookPipeline` 连接 `NasdaqItchUftAdapter`、可选扩展
`UftBookMarketDataEngine` 和稠密订单簿 `feed_*` 接口。
这些步骤都在同一线程内调用，避免队列交接和线程调度开销。它们只按交易所消息更新挂单，不在本地撮合。
只需要普通事件回调时，可以使用 `UftMarketDataEngine`，编译器会省去订单簿更新通道。
适配器会统计更新是否送达，并检查消息格式和容量是否足够。

| ITCH 事件 | 行情簿处理 | 策略收到回调时 |
|---|---|---|
| A / F 新增 | 插入对应价格档位尾部，不主动撮合 | 新订单已入簿 |
| X 部分撤单 | 减量；归零则删除，未归零保留时间顺序 | 更新后的剩余量 |
| D 删除 | 移除整个订单 | 删除后状态 |
| U 改单 | 原 ID 换新 ID，进入新档位队尾 | 一次完整更新，不暴露取消与新增之间的状态 |
| E / C 成交 | 按指定订单减量；不可打印成交也减量 | 成交后深度；可打印成交统计按 match ID 去重 |
| P / Q 非显示成交与交叉成交 | 不改挂单，只更新成交记录/统计 | 深度不变 |
| B 成交撤销 | 撤销相应成交统计，不恢复挂单或原时间优先级 | 当前深度不变 |

上述 B 和不可打印 C 的行为遵循
[Nasdaq TotalView-ITCH 5.0 官方规范](https://nasdaqtrader.com/content/technicalsupport/specifications/dataproducts/NQTVITCHSpecification.pdf)。
不能用已过滤的普通成交回调反推完整深度，因此使用独立的 `UftBookUpdate` 通道。

## 丢包后怎么办

- 必须从确认没有挂单的会话起点开始，传入会话标识 `session` 和起始序号。
  `ingest()` 的序号必须是**整个传输通道**的消息序号，不能使用适配器自己的
  单合约计数；其他合约和控制消息也必须经过序号检查。
- 例如应该收到第 10 条却先收到了第 12 条，程序不会先处理第 12 条，而是进入 `Recovering` 并暂停策略回调。
  补齐第 10、11 条并处理到第 12 条后，再通知策略。已处理消息的重传不会重复扣量或调用策略。
- `UftBookMoldFeed` 连接 `RecoveryWindow`：用固定大小的缓存暂存提前到达的数据报，产生补包请求，
  补齐后按序处理缓存中的消息；即使丢的是首包也能检测。调用方负责收包和实际发送补包请求。
- 消息格式错误、找不到对应订单或成交、价格超出配置范围、容量不足、会话变化或乱序缓存装满时，
  程序进入 `Faulted`，停止策略回调。此时订单簿可能只完成了一部分更新，不能继续拿来交易；
  需要新建实例，从确认完整的会话数据重新回放。**尚未实现 GLIMPSE 快照导入及自动重连**。
- `ready()` 只表示当前是否可以正常处理行情，不负责判断交易时段、停牌或风控条件。
  策略只能在回调中读取订单簿，不要在回调中再次调用 `ingest()`，也不要从其他线程修改它。

## 构建和测试

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel 4
ctest --test-dir build --output-on-failure
# 专门运行 UFT 行情簿测试及生成文件回放测试
ctest --test-dir build -R uft_orderbook --output-on-failure
```

测试检查新增、撤单、改单、成交、成交撤销，以及同价订单是否按先后顺序排列。
还会检查缺包时是否暂停策略、补齐后是否恢复，以及重复包、首包丢失、缓存装满和处理失败的情况。
另使用独立 `std::map` 参考模型进行 10,000 次随机状态转换，逐次检查全部档位数量、
订单剩余量、FIFO、活跃订单数和买卖一价。CTest 还会生成小型 ITCH 文件并运行实际回放入口。

## 回放真实 ITCH 文件

先准备从会话起点开始的完整 ITCH 文件，并确认目标合约的 locator、价格范围和最小价格变动单位。
程序只读文件，不下载数据。所有命令都在仓库根目录执行：

```bash
./build/qtrader_uft_orderbook_replay \
  /absolute/path/full-session.itch LOCATOR MIN_PRICE MAX_PRICE TICK MAX_ORDERS MAX_MATCHES
```

把大写参数替换成实际数字：

| 参数 | 填什么 |
|---|---|
| `LOCATOR` | ITCH 文件中目标合约的 stock locate 编号，不是股票名称 |
| `MIN_PRICE` / `MAX_PRICE` | 订单簿允许的最低价和最高价，以 1/10,000 美元为单位 |
| `TICK` | 相邻价格档位的间隔，单位同上；例如 0.01 美元填 100 |
| `MAX_ORDERS` | 最多同时保存多少笔挂单 |
| `MAX_MATCHES` | 最多保存多少个不同的成交编号，应覆盖整个会话 |

不想准备真实行情时，可以先运行以下测试。它会生成小文件，并自动检查回放结果：

```bash
ctest --test-dir build -R uft_orderbook --output-on-failure
```

数字参数均为正整数，价格单位为 1/10,000 美元。价格范围和 tick 从合约元数据配置，
不从输入价格差推断。文件按 2-byte 长度前缀读取，8 MiB 流式读缓冲，不加载全天到内存；
订单节点/价格档位和两份成交状态表在启动期按容量分配。成交撤销后仍保留簿侧 match 标记，
`MAX_MATCHES` 应覆盖整个会话的唯一成交数，而非仅未撤销成交数。
文件中的序号是程序按读取顺序自行编号的，无法发现文件原本就少了哪些记录。网络缺包检测使用 MoldUDP64 提供的序号。

订单簿目前通过了生成数据、随机差分和 ASan/UBSan 测试，尚未跑过真实全天文件或测量完整订单簿链路的性能。
事件分发的测试结果见 [性能测试说明](BENCHMARKS.md)。


## 共享内存与订单簿模拟链路

```text
生成行情 / WTS 逐笔委托文件
  → mmap 共享内存广播环（发布线程）
  → 共享内存读取线程 → SPSC 无锁队列
  → 价格时间优先订单簿 → 示例策略 → 模拟下单与撮合回报
                             （同一消费线程，不再跨线程）
```

实现位于 `src/Level2Pipeline.cpp`。提供 `qtrader_pipeline_reference`
和 `qtrader_pipeline_dense` 两个运行器，分别使用参考订单簿和稠密价格档位订单簿。
两个程序的区别只是订单簿实现，其余处理步骤相同。

```bash
# 两种订单簿各跑 10,000 条生成行情，逐条等待完成；用于功能验证
bash scripts/run_level2_pipeline.sh
# 单独运行稠密订单簿版本
./build/qtrader_pipeline_dense - 10000 paced
# 可选：读取同 ABI 的 WTSOrdDtlStruct 二进制文件（不是原始 ITCH）
./build/qtrader_pipeline_dense /absolute/path/orders.bin 10000 paced
```

文件模式读取整个文件，第二个数字仅控制生成模式的事件数。
省略 `paced` 参数可连续发布；两种模式都在环/队列满时等待，不覆盖尚未读取的数据。
示例策略每 1,024 条行情尝试买入 1 单位，生成行情测试检查全部事件处理完成及
预期模拟订单数、成交数、成交量；失败返回非零状态。

### 使用时注意

- Linux 使用临时文件支持的 `MAP_SHARED` mmap，正常退出删除文件；运行器是
  单进程三线程，没有启动独立的跨进程行情服务。广播组件另有多读者及 fork/mmap 测试。
- 输入委托会被当作模拟订单交给撮合器。需要重建真实行情订单簿时，请使用前述 `UftOrderBookPipeline`；
  不要把原始 ITCH 文件直接传给此模拟运行器。
- 示例价格按 10,000 倍转整数；稠密档位间距由输入价格差的最大公约数推断，
  不替代实盘合约元数据中的最小价格变动单位。
- 输出耗时包含计时操作、队列等待和模拟策略，仅用于查看示例的运行情况，不用于和 WonderTrader 做性能对比。
- 默认构建全部组件；只构建不含订单簿组件的工程可传 `-DQTRADER_BUILD_COMPONENT_PIPELINE=OFF`。
